## Overview

AI App Builder is a multi-agent software engineering system built using LangGraph, LangChain, Groq LLMs, and Pydantic.

The project explores how multiple AI agents can collaborate to transform a simple user request into a structured software project, including a validation stage that checks the AI-generated output before finishing.

The workflow consists of planning, architecture design, task generation, code generation, and review, using a stateful LangGraph workflow.

---

## Architecture

```
User Prompt
     ↓
Planner Agent
     ↓
Project Plan
     ↓
Architect Agent
     ↓
Task Plan
     ↓
Coder Agent (loops per file)
     ↓
Reviewer Agent
     ↓
Validated Project Files
```

---

## Planner Agent

The Planner Agent receives the user's request and converts it into a structured engineering plan.

The generated plan includes:
- Application name
- Description
- Tech stack
- Features
- Required files

The output is validated using Pydantic models.

---

## Architect Agent

The Architect Agent receives the planner output and generates implementation tasks.

Responsibilities:
- Analyze the project plan
- Break the project into implementation steps
- Generate file-level tasks
- Prepare instructions for the coding agent

---

## Coder Agent

The Coder Agent executes implementation tasks generated by the Architect Agent.

Responsibilities:
- Read existing files
- Generate code
- Write files to disk
- Track implementation progress using state

The coder agent uses LangGraph state management to process tasks sequentially.

---

## Reviewer Agent

The Reviewer Agent runs after the Coder Agent finishes, and validates the output before the workflow ends.

Responsibilities:
- Checks that every file the Coder was tasked with actually exists and is non-empty
- For Python files, parses them with Python's built-in `ast` module to catch syntax errors the Coder might have silently introduced
- For non-Python files, confirms existence, since syntax validation for arbitrary file types isn't attempted
- Produces a pass/fail report per file, printed to the console and returned in the graph state

This exists to catch a real failure mode of LLM-generated code: the Coder Agent can silently skip a file or write broken syntax, and without this step nothing catches that before the pipeline finishes.

---

## State Management

The project uses structured Pydantic models for agent communication.

### Plan
Stores:
- Name
- Description
- Tech stack
- Features
- Files

### TaskPlan
Stores:
- Implementation tasks
- File-level development instructions

### CoderState
Stores:
- Current task plan
- Current implementation step
- Current file content

This enables the coding agent to maintain progress across multiple implementation steps.

---

## Tools

The project includes custom filesystem tools:

### write_file()
Writes generated content to disk.

### read_file()
Reads file contents from the generated project. Used by the Reviewer Agent as well as the Coder.

### list_files()
Lists project files.

### get_current_directory()
Returns the current project directory.

These tools allow the coding agent to interact with the filesystem. All file operations are scoped to a `generated_project/` directory, with a path-safety check preventing writes outside that root.

## Example Workflow

Input:
```
Create a simple Flappy Bird style browser game using HTML, CSS, and JavaScript
with canvas. The bird falls due to gravity and flaps upward on click or
spacebar. Pipes scroll from right to left with gaps to fly through. Track
and display the score, and show a game over screen with a restart button
on collision.
```

Planner Output: a structured plan with the app name, tech stack (HTML/CSS/JS),
features (gravity, scrolling pipes, collision detection, scoring, restart),
and a list of files to generate.

Architect Output: implementation tasks broken down per file, with specific
instructions for classes, functions, and how they integrate with each other.

Coder Output:
```
index.html
style.css
script.js
README.md
```

Reviewer Output: confirmed all 4 files existed and were non-empty; the
generated game is committed in `agent/generated_project/` as a working demo.
